# API and security contract

The service runs in `agent-platform-credential-api`. Operation metadata and a resource-version-controlled capacity ledger contain no values or tokens. Operations live for 15 minutes, with at most 256 concurrent reservations across replicas. A crashed preparation retains its reservation until expiry. Cleanup removes expired operations using resource-version preconditions. Audit ConfigMaps record each save attempt's person, manager, namespace, Secret, mode and outcome. Export audit records before their namespace quota fills, retaining them according to the installation's audit policy.

Managers use `POST /v1/operations` and `GET /v1/operations/{id}` with an audience-bound ServiceAccount TokenRequest token lasting at most one hour. TokenReview authenticates the token, then a named-subject SubjectAccessReview checks `create` on `credential.giantswarm.io/v1/operations` in the service namespace. This is an authorization attribute, not a served Kubernetes resource or CRD. The manager must also appear in the configured identity-to-prefix mapping. Prefixes cannot overlap across managers. Status contains only operation ID, state, expiry and the configured standalone URL.

A creation carries `requestId`, `person` (issuer and subject), optional `actor` (the initiating issuer and subject verified by the manager), explicit organization and namespace, Secret name, `mode: apply`, a replacement flag, fields and every consumer's kind, name and exact HTTPS destinations. Managers are trusted to convey their verified caller and actor separately. Reusing a request ID with different metadata is refused. When tenancy is enabled, the namespace must carry the named organization's labels. Namespace and organization identity are bound through save; missing organization context never selects the platform namespace.

`fields` is a flat JSON Schema object: `type: object`, `additionalProperties: false`, `properties` and `required`. Properties support string, number, integer, boolean and file types, `title`, `description`, `writeOnly: true`, string lengths, string enumeration and numeric bounds. Nested objects, arrays, unknown schema keys and more than sixteen properties are refused. Each property maps to a Secret key. File values are UTF-8 strings, at most 64 KiB. File format `google-service-account` validates JSON service-account identity, the RSA PKCS#8 private key and Google's exact token endpoint. Creation metadata is limited to 128 KiB; browser saves retain the existing 2 MiB request bound.

The browser uses `/credential-api/signin`, `/credential-api/callback` and `/credential-api/api/operations/{id}`. The latter returns the owner-checked confirmation plus a CSRF token. Append `/save` or `/cancel` for POST actions. Saving takes the current `version`, destination `confirmation` digest and `values`; cancellation takes `version`. Every browser write requires an exact origin and `X-CSRF-Token`. Browser bearer tokens are not accepted. A portal login does not establish this service's session.

OAuth uses mcp-oauth's Dex provider and signed OIDC validation, authorization code, S256 PKCE, state and nonce. Encrypted server-side sessions and one-use OAuth state live in shared Valkey, scoped to the browser origin. Cookies are Secure, HttpOnly, host-only and SameSite=Lax. Only issuer and subject establish ownership; email, another identity of the same person and an admin's authority cannot transfer an operation. Delegated tokens cannot establish browser sessions. Kubernetes receives the person's own issuer-signed ID token, with no ServiceAccount fallback or impersonation.

Encryption is mandatory. Each encrypted record authenticates its complete Valkey key, including record kind, origin and cookie digest, so copying ciphertext to another session key cannot transfer an identity. OAuth state and sessions also carry authenticated expiry times. A session from a different configured issuer and an operation from a revoked manager mapping are refused.

The standalone URL always uses the configured credential origin. Direct ingress or Gateway API routes send the standalone host and the portal's `/credential-api` and `/credentials` paths to the service, bypassing Backstage. Both entry points show the installation, actor, manager, every consumer and exact destinations before fields. Manager descriptions use text nodes. The page has no third-party scripts, framing or caching, and clears entered values after save, error, cancellation or navigation. Values never enter URLs, browser storage, operation metadata, audit metadata or error responses. The service adds no telemetry containing request or response bodies and suppresses Kubernetes warning headers on credential transports.

Secret writes use only create and whole-object update as the person. Create dry runs discover existence without reads. A replacement confirmation records the version returned by a dry-run update; dry-run and real writes then require that version. Two independently confirmed replacements cannot silently overwrite each other. There are no credential get, list, watch, patch or delete calls. Authorization refusal says “Ask an admin”, who must initiate a separate setup under their own sign-in.

Saving first claims the operation through its ConfigMap resource version. A bounded detached write can finish after an HTTP disconnect, with its receipt and audit recorded separately. A recorded successful write can finish recovery after restart without another Secret write. A lost receipt keeps an explicit uncertain state; retrying it cannot become an unconditional replacement or read credential values. The service refuses a new write in the final 45 seconds of an operation's lifetime. Unsupported commit mode is rejected explicitly; encryption and ciphertext pickup belong to the next slice.

The Helm chart references an existing Secret containing `client-secret`, a random 32-byte base64 `session-key`, and authenticated `valkey-url`. Its ServiceAccount has metadata and review permissions only, with no Secret grant. Provision those inputs through the installation's existing secret management. Register exact OAuth callbacks at both origins and, on Dex, allow the separate client to request the Kubernetes audience through `trustedPeers`.
